## Abstract

This protocol proposes to use blockchains to **discover, choose, and interact with agents across organizational boundaries** without pre-existing trust, thus **enabling open-ended agent economies**.

Trust models are pluggable and tiered, with security proportional to value at risk, from low-stake tasks like ordering pizza to high-stake tasks like medical diagnosis. Developers can choose from different trust models: reputation systems using client feedback, validation via stake-secured re-execution, zero-knowledge machine learning (zkML) proofs, or trusted execution environment (TEE) oracles.

## Motivation

Model Context Protocol (MCP) allows servers to list and offer their capabilities (prompts, resources, tools, and completions), while Agent2Agent (A2A) handles agent authentication, skills advertisement via AgentCards, direct messaging, and complete task-lifecycle orchestration. However, these agent communication protocols don't inherently cover agent discovery and trust.

To foster an open, cross-organizational agent economy, we need mechanisms for discovering and trusting agents in untrusted settings. This ERC addresses this need through three lightweight registries, which can be deployed on any L2 or on Mainnet as per-chain singletons:

**Identity Registry** \- A minimal on-chain handle based on [ERC-721](./eip-721.md) that resolves to an agent's registration file, providing every agent with a portable, censorship-resistant identifier.

**Reputation Registry** \- A standard interface for posting and fetching feedback signals. Scoring and aggregation occur both on-chain (for composability) and off-chain (for sophisticated algorithms), enabling an ecosystem of specialized services for agent scoring, auditor networks, and insurance pools.

**Validation Registry** \- Generic hooks for requesting and recording independent validators checks (e.g. stakers re-running the job, zkML verifiers, TEE oracles, trusted judges).

Payments are orthogonal to this protocol and not covered here. However, examples are provided showing how payments can enrich feedback signals.

### Identity Registry

The Identity Registry uses ERC-721 for agent registration, making **all agents immediately browsable and transferable with NFTs-compliant apps**. Each agent stores its own *agentURI* on-chain, returned by the ERC-721 `tokenURI` method and updated with `setAgentURI()` as specified below. Each agent is uniquely identified globally by:

* *agentRegistry*: A colon-separated string `{namespace}:{chainId}:{identityRegistry}` (e.g., `eip155:1:0x742...`) where:
  * *namespace*: The chain family identifier (`eip155` for EVM chains)
  * *chainId*: The blockchain network identifier
  * *identityRegistry*: The address where the ERC-721 registry contract is deployed
* *agentId*: The ERC-721 tokenId assigned incrementally by the registry

Throughout this document, *tokenId* in ERC-721 is referred to as *agentId* and *tokenURI* in ERC-721 is referred to as *agentURI*. The owner of the ERC-721 token is the owner of the agent and can transfer ownership or delegate management (e.g., updating the registration file) to operators using the `approve` and `setApprovalForAll` mechanisms defined in ERC-721.

#### Agent URI and Agent Registration File

The *agentURI* MUST resolve to the agent registration file. It MAY use any URI scheme such as `ipfs://` (e.g., `ipfs://cid`), `https://` (e.g., `https://example.com/agent3.json`), or a base64-encoded `data:` URI (e.g., `data:application/json;base64,eyJ0eXBlIjoi...`) for fully on-chain metadata. When the registration uri changes, it can be updated with *setAgentURI()*.

The registration file MUST have the following structure:

  "image": "https://example.com/agentimage.png",

The *type*, *name*, *description*, and *image* fields at the top SHOULD ensure compatibility with ERC-721 apps. The number and type of *endpoints* are fully customizable, allowing developers to add as many as they wish. The *version* field in endpoints is a SHOULD, not a MUST.

Agents MAY advertise their endpoints, which point to an A2A agent card, an MCP endpoint, an ENS agent name, DIDs, or the agent's wallets on any chain (even chains where the agent is not registered).

#### Endpoint Domain Verification (Optional)

Since endpoints can point to domains not controlled by the agent owner, an agent MAY optionally prove control of an HTTPS endpoint-domain by publishing `https://{endpoint-domain}/.well-known/agent-registration.json` containing at least a `registrations` list (or the full agent registration file). Users MAY treat the endpoint-domain as verified if the file is reachable over HTTPS and includes a `registrations` entry whose `agentRegistry` and `agentId` match the on-chain agent; if the endpoint-domain is the same domain that serves the agent’s primary registration file referenced by `agentURI`, this additional check is not needed because domain control is already demonstrated there.

Agents SHOULD have at least one registration (multiple are possible), and all fields in the registration are mandatory.
The *supportedTrust* field is OPTIONAL. If absent or empty, this ERC is used only for discovery, not for trust.

#### On-chain metadata

The registry extends ERC-721 by adding `getMetadata(uint256 agentId, string metadataKey)` and `setMetadata(uint256 agentId, string metadataKey, bytes metadataValue)` functions for optional extra on-chain agent metadata:

```solidity
function getMetadata(uint256 agentId, string memory metadataKey) external view returns (bytes memory)
function setMetadata(uint256 agentId, string memory metadataKey, bytes memory metadataValue) external
```

When metadata is set, the following event is emitted:

```solidity
event MetadataSet(uint256 indexed agentId, string indexed indexedMetadataKey, string metadataKey, bytes metadataValue)
```

The key `agentWallet` is reserved and cannot be set via `setMetadata()` or during `register()` (including the metadata array overload). It represents the address where the agent receives payments and is initially set to the owner's address. To change it, the agent owner must prove control of the new wallet by providing a valid [EIP-712](./eip-712.md) signature for EOAs or [ERC-1271](./eip-1271.md) for smart contract wallets—by calling:

```solidity
function setAgentWallet(uint256 agentId, address newWallet, uint256 nonce, uint256 deadline, bytes calldata signature) external
```

The signed message MUST be the EIP-712 struct:

```solidity
AgentWalletSet(uint256 agentId,address newWallet,address owner,uint256 nonce,uint256 deadline)
```

The `nonce` MUST equal the current value of `getAgentWalletNonce(agentId)`, and implementations MUST increment that value on every successful `setAgentWallet()`. Without a nonce a spent signature remains valid until its `deadline` and can be replayed to revert a later wallet change: an owner rotating away from a compromised wallet can have that rotation undone by any approved operator still holding the earlier signature. Because the nonce makes each signature single-use, implementations need not bound `deadline` to limit a replay window.

```solidity
function getAgentWalletNonce(uint256 agentId) external view returns (uint256)
```

To read and clear the currently set wallet, the following functions are exposed:

```solidity
function getAgentWallet(uint256 agentId) external view returns (address)
function unsetAgentWallet(uint256 agentId) external
```

When the agent is transferred, `agentWallet` is automatically cleared (effectively resetting it to the zero address) and must be re-verified by the new owner.

### Reputation Registry

When the Reputation Registry is deployed, the *identityRegistry* address is set via `initialize(address identityRegistry_)` and publicly visible by calling:

```solidity
function getIdentityRegistry() external view returns (address identityRegistry)
```

The feedback given by a *clientAddress* to an agent consists of a signed fixed-point *value* (`int128`) and its *valueDecimals* (`uint8`, 0-18), plus optional *tag1* and *tag2* (left to developers' discretion to provide maximum on-chain composability and filtering), an *endpoint* URI, a file URI pointing to an off-chain JSON containing additional information, and its KECCAK-256 file hash to guarantee integrity. We suggest using IPFS or equivalent services to make feedback easily indexed by subgraphs or similar technologies. For IPFS URIs, the hash is not required.
All fields except *value* and *valueDecimals* are OPTIONAL, so the off-chain file is not required and can be omitted.

#### Giving Feedback

New feedback can be added by any *clientAddress* calling:

```solidity
function giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string calldata tag1, string calldata tag2, string calldata endpoint, string calldata feedbackURI, bytes32 feedbackHash) external
```

The *agentId* must be a validly registered agent. The *valueDecimals* MUST be between 0 and 18. The feedback submitter MUST NOT be the agent owner or an approved operator for *agentId*. *tag1*, *tag2*, *endpoint*, *feedbackURI*, and *feedbackHash* are OPTIONAL.

Where provided, *feedbackHash* is the KECCAK-256 hash (`keccak256`) of the content referenced by *feedbackURI*, enabling verifiable integrity for non-content-addressed URIs. For IPFS (or other content-addressed URIs), *feedbackHash* is OPTIONAL and can be omitted (e.g., set to `bytes32(0)`).

If the procedure succeeds, an event is emitted:

```solidity
event NewFeedback(uint256 indexed agentId, address indexed clientAddress, uint64 feedbackIndex, int128 value, uint8 valueDecimals, string indexed indexedTag1, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)
```

The feedback fields *value*, *valueDecimals*, *tag1*, *tag2*, and *isRevoked* are stored in the contract storage along with the feedbackIndex (a 1-indexed counter of feedback submissions that *clientAddress* has given to *agentId*). The fields *endpoint*, *feedbackURI*, and *feedbackHash* are emitted but are not stored. This exposes reputation signals to any smart contract, enabling on-chain composability.

When the feedback is given by an agent (i.e., the client is an agent), the agent SHOULD use the address set in the on-chain optional `agentWallet` metadata as the clientAddress, to facilitate reputation aggregation.

#### Read Functions

```solidity
function getSummary(uint256 agentId, address clientAddress, string tag1, string tag2, uint64 fromIndex, uint64 maxEntries) external view returns (uint64 count, int256 sumWad, uint64 nextIndex)
// Summarises ONE client's feedback for an agent. Reputation is always read per reviewer:
// an unfiltered summary across all clients is Sybil-prone. See Security Considerations.
// Inspects at most maxEntries indices starting at fromIndex, and returns nextIndex, the index
// to resume from. nextIndex == 0 means the client's feedback has been fully traversed.
// sumWad is the sum of the matching values, each normalised to 18 decimal places:
//   sumWad = SUM over matching entries of (value * 10^(18 - valueDecimals))
// The registry returns a sum, not an average, deliberately. A sum has exactly one correct
// answer, so independent implementations agree on it; and sums compose, so a consumer may
// walk pages, and several clients, and add the parts. Any averaging, weighting or decay is
// the consumer's choice, consistent with the Rationale below.

function readFeedback(uint256 agentId, address clientAddress, uint64 feedbackIndex) external view returns (int128 value, uint8 valueDecimals, string tag1, string tag2, bool isRevoked)

function readFeedbackRange(uint256 agentId, address clientAddress, string tag1, string tag2, bool includeRevoked, uint64 fromIndex, uint64 maxEntries) external view returns (uint64[] memory feedbackIndexes, int128[] memory values, uint8[] memory valueDecimals, string[] memory tag1s, string[] memory tag2s, bool[] memory revokedStatuses, uint64 nextIndex)
// Reads ONE client's feedback, in ascending feedbackIndex order, starting at fromIndex.
// tag1, tag2 and includeRevoked are optional filters; revoked feedback is omitted by default.
//
// These reads bound the WORK, not the results: a call MUST inspect at most maxEntries indices and
// MUST return nextIndex, the index to resume from, or 0 when the client has been fully traversed.
// It MAY therefore return fewer than maxEntries entries, or none, when filters exclude them.
//
// Bounding the results instead would not bound the cost. A count of all matching entries, or an
// offset into them, can only be computed by inspecting every entry, so the call would remain linear
// in the agent's total feedback however few rows it returned. Since these reads exist for on-chain
// consumption, and anyone may add feedback to an agent they do not own, an unbounded scan is both
// unusable at scale and cheaply griefable: a few thousand entries are enough to exceed a block.
//
// A consumer reads across clients by walking getClients(), and across one client by advancing
// fromIndex. Every call is then bounded by maxEntries regardless of how much feedback exists.
// Aggregation across clients, tags or time is an indexer's task, per the Rationale below.

function getResponseCount(uint256 agentId, address clientAddress, uint64 feedbackIndex, address[] responders) external view returns (uint64 count)
// agentId is the only mandatory parameter; others are optional filters.

function getClientCount(uint256 agentId) external view returns (uint64)

function getClients(uint256 agentId, uint64 offset, uint64 limit) external view returns (address[] memory clients)

function getLastIndex(uint256 agentId, address clientAddress) external view returns (uint64)
```

We expect reputation systems around reviewers/clientAddresses to emerge. **While simple filtering by reviewer (useful to mitigate spam) and by tag are enabled on-chain, more complex reputation aggregation will happen off-chain**.


### Validation Registry

**This registry enables agents to request verification of their work and allows validator smart contracts to provide responses that can be tracked on-chain**. Validator smart contracts could use, for example, stake-secured inference re-execution, zkML verifiers or TEE oracles to validate or reject requests.

When the Validation Registry is deployed, the *identityRegistry* address is set via `initialize(address identityRegistry_)` and is visible by calling `getIdentityRegistry()`, as described above.

#### Validation Request

Agents request validation by calling:

```solidity
function validationRequest(address validatorAddress, uint256 agentId, string requestURI, bytes32 requestHash) external
```

This function MUST be called by the owner or operator of *agentId*. The *requestURI* points to off-chain data containing all information needed for the validator to validate, including inputs and outputs needed for the verification. The *requestHash* is a commitment to this data (`keccak256` of the request payload) and identifies the request. All other fields are mandatory.

A ValidationRequest event is emitted:

```solidity
event ValidationRequest(address indexed validatorAddress, uint256 indexed agentId, string requestURI, bytes32 indexed requestHash)
```

#### Validation Response

Validators respond by calling:

```solidity
function validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag) external
```

Only *requestHash* and *response* are mandatory; *responseURI*, *responseHash* and *tag* are optional. This function MUST be called by the *validatorAddress* specified in the original request. The *response* is a value between 0 and 100, which can be used as binary (0 for failed, 100 for passed) or with intermediate values for validations with a spectrum of outcomes. The optional *responseURI* points to off-chain evidence or audit of the validation, *responseHash* is its commitment (in case the resource is not on IPFS), while *tag* allows for custom categorization or additional data.

validationResponse() can be called multiple times for the same *requestHash*, enabling use cases like progressive validation states (e.g., “soft finality” and “hard finality” using *tag*) or updates to validation status.

Upon successful execution, a *ValidationResponse* event is emitted with all function parameters:

```solidity
event ValidationResponse(address indexed validatorAddress, uint256 indexed agentId, bytes32 indexed requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag)
```

The contract stores *requestHash*, *validatorAddress*, *agentId*, *response*, *responseHash*, *lastUpdate*, and *tag* for on-chain querying and composability.

#### Read Functions

```solidity
function getValidationStatus(bytes32 requestHash) external view returns (address validatorAddress, uint256 agentId, uint8 response, bytes32 responseHash, string tag, uint256 lastUpdate)

function getSummary(uint256 agentId, address[] calldata validatorAddresses, string tag, uint64 fromIndex, uint64 maxEntries) external view returns (uint64 count, uint256 sumResponse, uint64 nextIndex)
// Summarises an agent's validations. validatorAddresses and tag are optional filters; an empty
// validatorAddresses matches any validator, and an empty tag matches any tag.
// Only requests that have received a response are counted; a pending request is not a zero.
// sumResponse is the sum of the matching responses, and count how many were summed. As in the
// Reputation Registry, the sum is returned rather than an average: a sum has exactly one correct
// answer, so independent implementations agree on it, and sums compose across pages. The consumer
// computes the mean as sumResponse / count and chooses its own rounding.

function getAgentValidations(uint256 agentId, uint64 fromIndex, uint64 maxEntries) external view returns (bytes32[] memory requestHashes, uint64 nextIndex)

function getValidatorRequests(address validatorAddress, uint64 fromIndex, uint64 maxEntries) external view returns (bytes32[] memory requestHashes, uint64 nextIndex)
```

These three reads bound the WORK, not the results, exactly as the Reputation Registry's reads do: a
call MUST inspect at most *maxEntries* entries starting at *fromIndex*, and MUST return *nextIndex*,
the index to resume from, or 0 when the list has been fully traversed. A call MAY therefore return
fewer than *maxEntries* entries, or none, when filters exclude them, and MUST NOT scan beyond its
window to find a match. Returning every entry would leave the cost linear in an agent's total
validations; since anyone may request validation of an agent they do not own, an unbounded scan is
cheaply griefable.

Incentives and slashing related to validation are managed by the specific validation protocol and are outside the scope of this registry.

## Rationale

* **Agent communication protocols**: MCP and A2A are popular, and other protocols could emerge. For this reason, this protocol links from the blockchain to a flexible registration file including a list where endpoints can be added at will, combining AI primitives (MCP, A2A) and Web3 primitives such as wallet addresses, DIDs, and ENS names.
* **Feedback**: The protocol combines the leverage of nomenclature already established by A2A (such as tasks and skills) and MCP (such as tools and prompts) with complete flexibility in the feedback signal structure.
* **Gas Sponsorship**: Since clients don't need to be registered anymore, any application can implement frictionless feedback leveraging [EIP-7702](./eip-7702.md).
* **Indexing**: Since feedback data is saved on-chain and we suggest using IPFS for full data, it's easy to leverage subgraphs to create indexers and improve UX.
* **Deployment**: We expect the registries to be deployed with singletons per chain. Note that an agent registered and receiving feedback on chain A can still operate and transact on other chains. Agents can also be registered on multiple chains if desired.

## Test Cases

Cases are given as input, expected output, and resulting state. Addresses are abbreviated;
`0xA` denotes the agent owner, `0xC` a client, `0xV` a validator, and `0xX` an unauthorized account.

### Identity Registry

**IR-1: `register` assigns sequential agentIds**

* Given an empty registry
* When `0xA` calls `register("ipfs://agent1")`
* Then the call returns `agentId = 0`, `ownerOf(0) == 0xA`, and `tokenURI(0) == "ipfs://agent1"`
* And it emits `Transfer(0x0, 0xA, 0)`, `Registered(0, "ipfs://agent1", 0xA)`, and `MetadataSet(0, "agentWallet", "agentWallet", 0xA)`
* When `0xA` calls `register("ipfs://agent2")`, the call returns `agentId = 1`

**IR-2: `agentWallet` defaults to the registrant**

* When `0xA` calls `register()`, `register(agentURI)`, or `register(agentURI, metadata)`
* Then `getAgentWallet(agentId) == 0xA` in each case

**IR-3: `agentWallet` is reserved**

* When `0xA` calls `setMetadata(agentId, "agentWallet", 0x...)`, the call reverts
* When `0xA` calls `register(agentURI, [{"agentWallet", 0x...}])`, the call reverts

**IR-4: `setAgentURI` updates the agentURI**

* Given `0xA` owns `agentId` with `tokenURI(agentId) == "ipfs://initial"`
* When `0xA` calls `setAgentURI(agentId, "https://example.com/agent.json")`
* Then `tokenURI(agentId) == "https://example.com/agent.json"` and `URIUpdated(agentId, "https://example.com/agent.json", 0xA)` is emitted
* When `0xX` calls `setAgentURI(agentId, ...)`, the call reverts

**IR-5: `setAgentWallet` requires proof of control of the new wallet**

* Given `0xA` owns `agentId`, `getAgentWalletNonce(agentId) == n`, and `0xW` signs the EIP-712 `AgentWalletSet(agentId, newWallet, owner, nonce, deadline)` struct with `nonce = n`
* When `0xA` calls `setAgentWallet(agentId, 0xW, n, deadline, signature)` with `block.timestamp <= deadline`
* Then `getAgentWallet(agentId) == 0xW`, `getAgentWalletNonce(agentId) == n + 1`, and `MetadataSet(agentId, "agentWallet", "agentWallet", 0xW)` is emitted
* When the signature is produced by any address other than `newWallet`, the call reverts
* When `block.timestamp > deadline`, the call reverts
* When the caller is neither owner nor an approved operator, the call reverts
* When `nonce != getAgentWalletNonce(agentId)`, the call reverts

**IR-5b: a spent `setAgentWallet` signature cannot be replayed**

* Given `0xW1` signed at `nonce = n` and `0xA` used it, so `getAgentWallet(agentId) == 0xW1` and the nonce is `n + 1`
* And `0xW2` signed at `nonce = n + 1` and `0xA` used it, so `getAgentWallet(agentId) == 0xW2`
* When `0xA`, or any approved operator, resubmits `0xW1`'s original signature at `nonce = n`
* Then the call reverts and `getAgentWallet(agentId)` remains `0xW2`
* Without a nonce this replay succeeds while `block.timestamp <= deadline`, silently reverting the wallet to `0xW1`

**IR-6: `agentWallet` is cleared on transfer**

* Given `getAgentWallet(agentId) == 0xW`
* When `0xA` transfers `agentId` to `0xB`
* Then `getAgentWallet(agentId) == address(0)` and `getMetadata(agentId, "agentWallet")` returns empty bytes

### Reputation Registry

**RR-1: `giveFeedback` stores feedback under a 1-indexed counter**

* Given `agentId` is registered and owned by `0xA`
* When `0xC` calls `giveFeedback(agentId, 85, 0, "quality", "speed", "https://agent.example", "ipfs://f1", 0x...)`
* Then `getLastIndex(agentId, 0xC) == 1` and `readFeedback(agentId, 0xC, 1)` returns `(85, 0, "quality", "speed", false)`
* And `NewFeedback(agentId, 0xC, 1, 85, 0, "quality", "quality", "speed", "https://agent.example", "ipfs://f1", 0x...)` is emitted
* A second call from `0xC` stores at index `2`

**RR-2: self-feedback is rejected**

* When `0xA` (the owner of `agentId`), or an operator approved for `agentId`, calls `giveFeedback(agentId, ...)`
* Then the call reverts

**RR-3: `agentId` must exist and `valueDecimals` must be 0..18**

* When `0xC` calls `giveFeedback` for an unregistered `agentId`, the call reverts
* When `0xC` calls `giveFeedback(agentId, value, 19, ...)`, the call reverts

**RR-4: `revokeFeedback` marks feedback revoked**

* Given `0xC` gave feedback at index `1`
* When `0xC` calls `revokeFeedback(agentId, 1)`
* Then `readFeedback(agentId, 0xC, 1)` returns `isRevoked == true` and `FeedbackRevoked(agentId, 0xC, 1)` is emitted
* A second `revokeFeedback(agentId, 1)` reverts

**RR-5: `getSummary` summarises one client and returns a composable sum**

* Given `0xC1` gave `80` and `90`, both with `tag1 = "service"`, `tag2 = "fast"`, `valueDecimals = 0`
* When `getSummary(agentId, 0xC1, "service", "fast", 1, 100)` is called
* Then it returns `count = 2`, `sumWad = 170 * 10^18`, and `nextIndex = 0`, meaning the client is fully traversed
* And the consumer computes the mean itself: `sumWad / count = 85 * 10^18`
* An empty `tag1` or `tag2` matches any value for that tag

**RR-5b: `getSummary` composes across pages and across clients**

* Given `0xC1` gave `80` and `90`, and `0xC2` gave `100`, all with the same tags
* When `getSummary(agentId, 0xC1, "service", "fast", 1, 1)` returns `count = 1`, `sumWad = 80 * 10^18`, `nextIndex = 2`
* And `getSummary(agentId, 0xC1, "service", "fast", 2, 1)` returns `count = 1`, `sumWad = 90 * 10^18`, `nextIndex = 0`
* And `getSummary(agentId, 0xC2, "service", "fast", 1, 100)` returns `count = 1`, `sumWad = 100 * 10^18`, `nextIndex = 0`
* Then the parts add to `270 * 10^18` over `3` entries, identical to reading them in one call
* This is why the registry returns a sum: an average cannot be recombined from pages

**RR-5c: a call inspects at most `maxEntries` indices**

* Given `0xC1` gave 1,000 entries, of which only index `1,000` has `tag1 = "rare"`
* When `getSummary(agentId, 0xC1, "rare", "", 1, 10)` is called
* Then it returns `count = 0` and `nextIndex = 11`
* The call MUST NOT scan ahead to find a match: the cost of every call is bounded by `maxEntries`,
  not by how much feedback exists or how selective the filter is
**RR-6: `readFeedbackRange` reads one client in index order**

* Given `0xC` gave `70` (`tag1 = "quality"`), `80` (`tag1 = "speed"`), and `90` (`tag1 = "reliability"`)
* When `readFeedbackRange(agentId, 0xC, "", "", false, 1, 100)` is called
* Then it returns `feedbackIndexes = [1, 2, 3]`, `values = [70, 80, 90]`, `tag1s = ["quality", "speed", "reliability"]`, and `nextIndex = 0`
* When `readFeedbackRange(agentId, 0xC, "", "", false, 2, 1)` is called, it returns only `values = [80]` and `nextIndex = 3`
* Revoked feedback is omitted unless `includeRevoked` is `true`
* Reading every client means walking `getClients(agentId, offset, limit)` and repeating the above per client

**RR-7: `appendResponse` is permissionless and counted per responder**

* Given `0xC` gave feedback at index `1`
* When `0xR1` and `0xR2` each call `appendResponse(agentId, 0xC, 1, "ipfs://r", 0x...)`
* Then `getResponseCount(agentId, 0xC, 1, [])` returns `2`, and `getResponseCount(agentId, 0xC, 1, [0xR1])` returns `1`
* Responses may be appended to revoked feedback

### Validation Registry

**VR-1: `validationRequest` is restricted to the agent owner or an operator**

* Given `agentId` is owned by `0xA`
* When `0xA` calls `validationRequest(0xV, agentId, "ipfs://req", requestHash)`
* Then `getValidationStatus(requestHash)` returns `validatorAddress = 0xV`, `agentId`, `response = 0`
* And `ValidationRequest(0xV, agentId, "ipfs://req", requestHash)` is emitted
* When `0xX` calls `validationRequest` for `agentId`, the call reverts
* A second request reusing `requestHash` reverts

**VR-2: `validationResponse` is restricted to the requested validator and bounded 0..100**

* Given a request exists for `requestHash` with validator `0xV`
* When `0xV` calls `validationResponse(requestHash, 100, "ipfs://resp", responseHash, "passed")`
* Then `getValidationStatus(requestHash)` returns `response = 100`, `responseHash`, `tag = "passed"`
* And `ValidationResponse(0xV, agentId, requestHash, 100, "ipfs://resp", responseHash, "passed")` is emitted
* When `0xX` calls `validationResponse(requestHash, ...)`, the call reverts
* When `response > 100`, the call reverts
* `response = 0` and intermediate values such as `67` are accepted

**VR-3: `validationResponse` may be called repeatedly for the same request**

* Given `0xV` responded `80` with `tag = "soft_finality"`
* When `0xV` calls `validationResponse(requestHash, 100, ..., "hard_finality")`
* Then `getValidationStatus(requestHash)` returns `response = 100` and `tag = "hard_finality"`

**VR-4: lookups track requests per agent and per validator**

* Given `0xA` requested validation from `0xV1` and `0xV2` for `agentId`
* Then `getAgentValidations(agentId, 1, 100)` returns both request hashes and `nextIndex = 0`
* And `getValidatorRequests(0xV1, 1, 100)` returns only the request addressed to `0xV1`

**VR-5: `getSummary` sums responded validations and composes across pages**

* Given `0xV1` responded `80` and `90` for `agentId`, and a third request to `0xV2` is left pending
* When `getSummary(agentId, [], "", 1, 100)` is called
* Then it returns `count = 2`, `sumResponse = 170`, and `nextIndex = 0`: the pending request is not counted as a zero, and the consumer computes the mean itself as `sumResponse / count = 85`
* As in the Reputation Registry, the registry returns a sum, not an average, so independent implementations agree and pages recombine: `getSummary(agentId, [], "", 1, 1)` then resuming at the returned `nextIndex` yields the same total
* An empty `validatorAddresses` matches any validator, and an empty `tag` matches any tag
* Like the Reputation reads, the call inspects at most `maxEntries` entries and returns `nextIndex` to resume from

## Security Considerations

* Sybil attacks are possible, inflating the reputation of fake agents. The protocol's contribution is to make signals public and use the same schema. We expect many players to build reputation systems, for example, trusting or giving reputation to reviewers (and therefore filtering by reviewer, as the protocol already enables).
* On-chain pointers and hashes cannot be deleted, ensuring audit trail integrity
* Validator incentives and slashing are managed by specific validation protocols
* While this ERC cryptographically ensures the registration file corresponds to the on-chain agent, it cannot cryptographically guarantee that advertised capabilities are functional and non-malicious. The three trust models (reputation, validation, and TEE attestation) are designed to support this verification need
